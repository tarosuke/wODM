## ジオメトリ

動きとしては特定奥行きにある平面上を移動する。カーソルが表示されるのは原点とその点を結ぶ線の交点を持つPaneの上になる。

Paneのstaticメンバで持てばいいだろうか。

### Widgetの検出

Windowにおいてはジオメトリで示した点への直線との交点を用いる。
また子要素を探索する条件は以下のいずれか。
1. 自身との交点を持つ
2. 与えられた「厚み」の直方体のいずれかの面との交点を持つ

実際の処理はslab法が妥当であろう。直線を媒介変数表記(原点とベクトル)各軸ごとに直線がその値になる媒介変数を求めて(slabの位置をベクトルのその軸の要素で割るる)軸ごとの近い距離同士の最大値、遠い距離同士の最小値を求めてそれらが範囲を持つか判定するものだ。

なお、slab法では直線とslabが並行になる例外処理があるが、ポインタへのベクトルで0になっている要素をスキップすることで実装する。初期値を矛盾値(最小無+限大、最大-無限)にしておけばいい。

### 戻り値が面倒なのでイベントを直接投げる

ポインティングデバイスで発生するイベントは仮想画面上の座標とボタンとモディファイアキー情報を合わせた`PtEvent`。これを`OnEvent`ハンドラに投げる。
```C++
bool OnEvent(const PtEvent&,const tb::Vector<3,float>& origin);
```

`origin`は原点。グローバル座標での原点は自明であり`PtEvent`には向きしか入っていないのでローカル座標への変換に使う。

面あるいは壁面にヒットしたら子要素へ投げ、子要素でヒットしなければ(子要素すべての`OnEvent`が偽を返したら)自らのイベントとして個別のイベントハンドラを呼ぶ。

## レイアウト

縦横のリストをコンテナにして要素を詰めていくとコンテナが自動で配置していく。

サイズ指定は画素単為のSpreadではなく画素or比率指定(値はfloat)で絶対値が1.0を超えているなら画素指定、絶対値が1.0以下なら割合指定。負数なら逆寄せ指定。

`spacing`引数にて子要素の上下左右に確保すべき隙間を指定。子要素間で共有されないmerginではなく隙間なのでコンテナ要素の内側だけでなく子要素の間隔もこの値になる。

### 奥行きのレイアウト

#### 子要素が奥行き方向に並ばない場合

親要素が持つ奥行きの半分を奥行きとして割り当てられ、その位置は親要素の持つ奥行きの半分となる。無限に子要素が割り当てられた場合その奥行きの合計が親要素の持つ奥行きと一致するので親要素の奥行きや姉妹要素の奥行きを変更する必要がないのがこの方針を選択した理由である。

#### 子要素が奥行き方向に並ぶ場合

奥行きが子要素へ半分継承される代わりに姉妹要素に1/2^nが分配される。追加や削除、順序変更で全要素の奥行きが再配置される。これはそれぞれの子要素に再帰的に波及する。

変更の波及範囲が広くてあまり使いたくないのでこの配置方針の代表的応用であるタブは使わず代わりにメニューから選択するようになるかも知れない。

#### `Window`の場合

`Window`は「子要素が奥行き方向に並ぶ」が、この場合は親要素の奥行き制限がないため単純に先頭から「Windowの占有奥行き」の間隔で整列される。要素が抜けたり追加されたりした場合は再配置されるが`Vishov`が占有する奥行きは不変であるため再配置は子要素には波及しない。


### 追加順

`Item`は例えば水平コンテナなら左に追加されるとコンテナの開始点が進み、右に追加すると終了点が戻る。なので`Item`は残りサイズが決定する順に追加する。なお開始点、終了点は`Item`の追加で確定するので、逆側の`Item`が存在しない場合に限り`Item`はコンテナのサイズを超えて追加できる。

例えば左右に要素があって中央の残りをもう一つの要素が占める場合、左右端の要素を先に追加し、最後に中央の要素を幅1.0指定で追加する。

# ConvasPaneにおけるテクスチャ更新

## priorityUpdateingとupdateCompleted

priorityUpdatingは可視部分を優先更新、updateCompletedはUpdateAllがその完了を知るためのフラグである。以下のように運用する。

1. priorityUpdateingであるときはshownでないPaneはテクスチャを更新しない。
2. shownなPaneにUpdateRegionを登録する時にpriorityUpdateingを立てる。
3. shownなPaneが更新を中断した場合updateCompletedを落とす。
4. UpdateAll時にupdateCompletedを立て、終了時に立ったままであったらpriorityUpdateingを落とす。

# updateRegion

更新範囲はupdateRegionにて管理される。

* 更新登録時
   * 更新updateRegionに更新対象を論理和
   * shwnならpriorityUpdateingを立てる
* 更新時
  * 更新可能サイズに従い更新ライン数を決定
  * updateRegionの幅、更新ライン数の領域を更新
  * 更新した分だけupdateRegionを削る
  * updateRegionが残っていたらupdateCompletedを落とす

# 自動試験

DummyHMDを修正してテストドライバとする。スタブは適宜構成し、Core::Runの引数としてセットアップメソッドを与えるようにする(既定はCore内蔵の「new Login」するメソッド)。

## ユースケースの記述法

DummyHMDに試験のためのWidgetを差分で追加し、これをテストドライバスタブとする。別のクラスにすると状態及び試験管理変数の可視性に問題が生じることが予想されるため、一体のクラスとして作成する。

試験コードのmainにてドライバスタブの構築後、`Finish`が呼ばれるのでその中でイベントを進め、検証する。
+ tickを読み取りその値を持ってタイミングを測る
+ テストドライバにはイベントを発生させるためのメソッドがある
  + イベントを発生する時にテストシーケンス番号を設定する
  + 発生できるイベントは今のところ以下のようなものを計画している
    + ポインティングデバイスの移動
    + ボタンのDown/Up
    + キーDown/Up/Repeat
+ スタブメソッドが呼ばれるのでその内容およびテストシーケンス番号をチェックして期待通りであることを`assertEQ`などで確認する。




# 進捗表示

Progressクラスが存在するときはカーソルの周囲にプログレスリングが表示される。これは0$-100%あるいは0.00-1.00までの百分率表示で、複数のProgressが存在する場合その平均となる。またProgressが完了した場合はそのProgressがなくなっても全体が完了するまでは引き続き100%として扱われる。

現状ではリングの下の方に数値表示、0%の部分と100%の部分に線、残りの部分に環状に白い枠、そのすぐ外側に進捗リングという構成を考えている。

進捗はProgressのインスタンスを通じて設定できる。単純にインスタンスがなくなった場合は失敗扱いとなる。これは異常修了などを想定した動作である、完了とするにはインスタンスがなくなる前に完了を設定する必要がある。

進捗の変化は差分の1/nが変化するようなよくあるもの。差分が正の場合青で、負の場合は黄で表示される。

## 失敗

Progressが完了を設定せずに消滅した場合、そのインスタンスは集計から除外される。この変化の間は黄色表示となる。実際には失敗通知が必要なのでProgressにはこのあたりを一元的に扱える窓口であるべきであると考えている。
